Проверено: `docs/architecture.md`, ADR-001..ADR-007, `.crew/stack/security.md`, `.crew/stack/nextjs.md`, `.crew/stack/deploy.md`, `.crew/brief.md` (роли, Risks), скелет (`.gitignore`, `.env.example`, `vercel.json`, `src/app/api/health`, `src/server/clock.ts`).
Сканеры: `npm run audit` (`npm audit --omit=dev`) — 0 уязвимостей; поиск секретов `git grep` по шаблону ключей/токенов — пусто; `.env*` и `/data/` в `.gitignore`, в git только `.env.example` с пустым токеном.

## Модель угроз (из брифа)

Паролей нет: открытая ссылка, пользователь выбирается по имени, список имён публичен (`GET /api/users`). Значит, «изоляция пользователей» защищает от **случайного** смешения данных (AC-20) и от ошибок кода, а не от посетителя, который выберет чужое имя. Подделка cookie `uid=<число>` даёт ровно то же, что выбор имени в переключателе, — новой уязвимости не создаёт. Это принятый риск брифа (Risks: «любой может видеть данные по имени пользователя; не вводить личные данные»), не находка ревью.

Что ревью обязано гарантировать в этой модели: сервер никогда не вернёт и не изменит запись не того пользователя, чей `uid` в cookie; клиент не может указать владельца или цель разрушающего действия; секреты (токен Turso) не утекают; публичный хостинг нельзя тривиально положить.

## 1. Роли × действия

Одна роль. Проверка — на сервере, в каждом запросе.

| Сущность | Чтение | Изменение | Где проверка |
|---|---|---|---|
| users (id, name) | все (переключатель) | создание любым посетителем, `POST /api/session` | Zod `name` 1–40; уникальность по `name_key` |
| records | только владелец | только владелец; удаление — после «да» в диалоге | `requireUserId()` в route handler → репозиторий с `userId` в `WHERE`, включая update/delete по id (security.md п.2) |
| dialog_messages | только владелец | только владелец (`/api/chat`, `/api/dialog/reset`) | то же |
| dialog_states | только владелец | только сервер | `user_id` PK; цель удаления/выбора/фокус — только из состояния на сервере (ADR-003, security.md п.8) |

Покрыто архитектурой: `uid` берётся только из httpOnly cookie, проверяется существование пользователя, без cookie 401 (`nextjs.md`, security.md п.1); `PATCH /api/records/[id]` для чужой записи — 404; поиск получает уже отфильтрованные по `userId` записи (ADR-005); конфликты — против встреч пользователя.

Что буду проверять в задачах (не находка, а критерий приёмки на этапе security):
- id из `state_json` (`recordId`, `candidateIds`, `conflictIds`) и `focus_record_id` применяются **через те же репозитории с `userId`**, а не через выборку «по id». Состояние пишет только сервер, но это второй рубеж на случай ошибки в автомате.
- `uid` из cookie разбирается Zod (`z.coerce.number().int().positive()`), неверное значение или несуществующий пользователь — 401, не 500.
- `[id]` в `PATCH /api/records/[id]` — тоже Zod (целое > 0), тело `{ done: boolean }` — строгая схема.
- Есть тест изоляции: «Борис» не видит записи «Анны» в `GET /api/records`, `GET /api/dialog`, поиске через `/api/chat`, и `PATCH` записи «Анны» от «Бориса» даёт 404.

## 2. Аутентификация

- Пароли — нет по брифу (Out of scope), хранения паролей нет; хэширование неприменимо.
- Сессия: cookie `uid`, httpOnly, `sameSite: "lax"`, `secure` в production, `path: "/"`, 1 год. Подпись не нужна (см. модель угроз).
- Перечисление аккаунтов: список имён публичен намеренно (переключатель, AC-20). Принято.
- Выход: отдельного нет, переключение пользователя перезаписывает cookie. Достаточно для прототипа.

## 3. Данные

- Хранится: имена (свободный текст), заголовки записей, даты/время, реплики диалога (до 500 символов) и снимки `items_json`. Реальные персональные данные не предполагаются; CSV — демонстрационный, принадлежит «Демо».
- Показ: всё только владельцу, кроме списка имён.
- Хранение: бессрочно. Удаление записи — физическое; «Новый диалог» стирает реплики и состояние. Пользователя удалить нельзя (не требуется брифом).
- Экспорта нет.
- Внешние передачи: распознавание речи Chrome отправляет звук в Google (бриф, Risks) — нужно упомянуть в README; LLM нет (ADR-007), текст не уходит третьим лицам.

## 4. Входы

Все точки входа перечислены в `docs/architecture.md#4-api`; для каждой задана Zod-схема в `src/shared/schemas.ts` и лимиты (`text` 1–500, `name` 1–40); ошибки — код и русское сообщение без деталей, 500 без стека (architecture §10, security.md п.6). SQL — только билдер Drizzle / `sql`-шаблон с параметрами (security.md п.4). Вывод — текст через React, без `dangerouslySetInnerHTML` (п.5). Изменяющие действия — POST/PATCH; GET только читают. Тестовых/служебных маршрутов в production не предусмотрено — так и должно остаться.

## 5. Секреты и конфигурация

- Единственный секрет — `DATABASE_AUTH_TOKEN` (Turso): только env (Vercel settings / локальный `.env`), `.env*` в `.gitignore`, `.env.example` с пустым значением. Никаких `NEXT_PUBLIC_*`.
- `vercel.json` запускает миграции и сид при сборке — токен нужен в окружении сборки; скрипты не должны печатать `DATABASE_URL`/токен в лог.
- `APP_NOW` в production запрещён (`deploy.md`); `GET /api/health` отдаёт только `ok` и `now`.

## 6. Находки

Критических и высоких нет.

### Medium (не блокируют; оркестратор может завести задачи)

- **M1. Нет ограничения на объём со стороны анонимного посетителя.** Публичная ссылка без входа: скрипт может создать неограниченно пользователей (`POST /api/session`) и записей/реплик (`POST /api/chat`), исчерпав квоту Turso Free и сделав поиск медленным (ADR-005 загружает все записи пользователя на каждый запрос). Ожидаемое исправление (дешёвое): лимит записей на пользователя (например, 2000, сверх — ответ «Достигнут лимит записей»), хранить в `dialog_messages` не больше N последних реплик на пользователя (например, 200), простой лимит частоты на IP для `POST /api/session` и `POST /api/chat` (в памяти процесса достаточно).
- **M2. Заголовки безопасности не заданы.** В `next.config.ts` добавить `poweredByHeader: false` и `headers()` с `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY` (или CSP `frame-ancestors 'none'`), `Permissions-Policy: microphone=(self)`.
- **M3. Граница клиент/сервер держится на договорённости.** Правило «клиент импортирует только `src/shared` и `src/client`» стоит закрепить в ESLint (`no-restricted-imports` для `src/components/**`, `src/client/**`, `src/app/page.tsx` → запрет `@/server/*`, `@/db/*`), чтобы `src/db/client.ts` с токеном случайно не попал в клиентский бандл.

### Low / info

- **L1. Login CSRF.** Сторонний сайт может отправить `POST /api/session` и переключить посетителя на другое имя. Ущерб минимален (данных-секретов нет); `sameSite: "lax"` защищает остальные POST. Желательно: route handlers принимают только `Content-Type: application/json` и/или сверяют `Origin` с хостом.
- **L2. Снимки `items_json`.** Заголовок удалённой записи остаётся в истории диалога до «Нового диалога». Соответствует AC-15 (из списка и поиска исчезает); упомянуть в README достаточно.
- **L3. ReDoS в правилах NLU.** Вход ограничен 500 символами, но регулярные выражения в `src/server/nlu` не должны содержать вложенных квантификаторов вида `(a+)+`.
- **L4. Похожие имена.** `normalize(name)` не склеивает кириллицу и латиницу («Анна» / «Аннa»). Без паролей это не угроза; можно ограничить имя кириллицей/латиницей/цифрами/пробелом/дефисом в Zod.
- **L5. Логи.** `console.error` на 500 не должен включать текст реплики и значения env (security.md п.6) — проверю в задачах.
- **L6. Голос.** README должен сказать, что Chrome/Edge отправляют звук в облачный сервис распознавания (бриф, Risks).
